# Blux Beta Release

Verify that `origin` is `benkuper/Blux` and read applicable `AGENTS.md` instructions. If Windows Git reports an ownership mismatch on a verified checkout, scope `git -c safe.directory=<absolute-path>` to the command. A request to release a beta authorizes preparing the release commit, pushing its tag, monitoring CI, and publishing the two metadata files once the packages are available. A request to create or edit this skill authorizes skill changes only.

## Select the release source and version

- Inspect staged and unstaged changes, untracked files, and submodules. Fetch the relevant branch and tags from `origin`. Use the requested commit or branch when specified. For a plain beta request on `main`, use the current committed `main` if it contains `origin/main`, or `origin/main` if local `main` is strictly behind it. Resolve divergence before tagging. If pending application changes could be part of the intended beta, clarify their inclusion. Preserve the user's index and working tree, using a separate worktree when the release source differs or generated files overlap pending edits.
- Honor an explicit beta version. Blux uses `MAJOR.MINOR.PATCHbN` tags without a `v` prefix. For an unspecified new beta, reconcile the release source's `Blux.jucer` version, current published beta, and local and remote tags. Use the source's already-prepared beta if it is newer than the published beta and untagged. Otherwise, increment the highest beta counter in the intended development series numerically, or use `b1` for a new series. If a matching tag or checkpoint represents an interrupted release of the intended source, resume that release. Compare an existing tag's peeled commit with the intended release and report conflicts. Tags are immutable.
- Find the last published beta tag on the release ancestry. Review its full commit range through the selected source, including relevant submodule changes, and read diffs where commit messages leave behavior unclear. Write concise changelog strings in the existing style. Report the chosen version, source SHA, and comparison tag before pushing. Confirm the release commit's recursive submodule revisions are fetchable from their configured remotes by CI.

## Regenerate the project and prepare metadata

1. Set the `JUCERPROJECT` `version` in `Blux.jucer`. Run a compatible `Projucer.exe --resave <absolute-path-to-Blux.jucer>` and require a successful full resave. The current project needs a Projucer that supports the VS2026 exporter. Check `.github/actions/set-variables/action.yml` and `.github/workflows/build.yml` at the release source for the JUCE fork and ref. CI currently uses `benkuper/JUCE` at `juce8_local`, checked out as `JUCE/`. A different branch of the shared `D:\Projects\Dev\JUCE` checkout can be missing modules such as `juce_audio_processors_headless`. In the isolated worktree, export `modules/` from the matching JUCE ref into `JUCE/` and temporarily point the VS2026 exporter's empty JUCE module paths at `JUCE/modules`. This uses the matching modules and keeps the shared checkout on its current branch. Restore those temporary VS2026 path edits after generation, preserving the release version and all CI module paths.
2. Inspect the generated diff. Verify the version string and numeric base version where applicable in `JuceLibraryCode/JuceHeader.h`, the VS2022 CI project and resources, macOS project and plist, and the Linux and both Raspberry Pi Makefiles. Verify the local VS2026 exporter too and honor Git's ignore rules for its output. Check that tracked exporter files retain their CI-relative JUCE paths and include the expected module sources. Commit the intended version and generated changes if needed. If the chosen source already contains identical release output, tag that commit. Keep CI enabled for the tagged commit.
3. Work with `site/releases/update.json` and `site/user/config/downloaddata.yaml` from the original checkout. Compare with the published metadata before preparing updates when available. Reconcile differences so publication preserves independent website edits. In the JSON, replace `betaversion.version` and `betaversion.changelog`. When the version changes, archive the outgoing beta once with its original notes. The updater reads `archives` backward and expects flat `{ "version": "...", "changelog": [...] }` records. Keep historical releases in ascending version order, comparing beta counters numerically. Flatten legacy wrapped entries and collapse identical duplicates without losing notes. Reconcile conflicting notes before removing duplicates. Exclude the current beta and stable from `archives` and preserve `stableversion`, extension settings, and unrelated fields.
4. In the YAML, set `betaversion` and ensure `betaavailable` is true. Add the outgoing beta once to `olderversionsbeta`, newest first, and keep the new current beta out of that list. Preserve existing download buttons, stable settings, and other fields. Resuming the same beta leaves its archive and older-version entries unchanged. Parse both files and verify the new version matches the tagged application, the outgoing notes and history are retained, and each advertised beta button maps to a CI package.
5. Keep the ignored `site/` tree and its SFTP profile out of Git. Freeze both validated files outside the repository. Record their paths, hashes, release version, and commit SHA so the release can resume after CI or an interruption.

## Push the tag and verify the packages

- Push only an annotated tag named exactly for the chosen beta with `git push origin refs/tags/<version>`. Verify the remote tag peels to the intended commit. If the push result is ambiguous, check the remote before retrying.
- Find the `build.yml` push run for the exact tag and commit SHA. For example, use `gh run list --repo benkuper/Blux --workflow build.yml --branch <version> --event push --commit <sha> --json databaseId,headBranch,headSha,status,conclusion,url`. Record the run ID and URL. Branch builds produce `bleedingedge` packages.
- Derive the expected jobs from the workflow at the tag. Currently these are Windows x64, macOS Intel and Apple Silicon, Linux x64, and Raspberry Pi armhf and aarch64. Wait for all required jobs and uploads to succeed. Poll at intervals of at most 60 seconds and keep the user informed. If CI fails, report the job and logs and retain the checkpoint. Resume the same tag after resolving the issue.
- Confirm the actual versioned packages are available before publishing metadata. CI's upload action uses `curl` without `--fail`, so a green job alone does not prove that the server accepted its package. Build the expected names from `.github/actions/set-variables/action.yml`, `build.yml`, and `buttonsbeta`. Currently they are `Blux-win-x64-<version>.exe`, `Blux-osx-{intel,silicon}-<version>.pkg`, and `Blux-linux-{x64,armhf,aarch64}-<version>.AppImage` under `https://benjamin.kuperberg.fr/blux/download/app/`. Check HTTP status and that the responses are packages, using a small ranged GET if HEAD is inconclusive. Required job failures, skipped jobs, and missing packages block metadata publication.

## Publish both metadata files over SFTP

- Read connection settings directly from `site/.vscode/sftp.json` in the upload process. Honor its protocol, host, port, authentication, `remotePath`, and server identity verification. Keep credentials out of tool output, command-line arguments, and commits. Treat `site/` as the local root. Append `user/config/downloaddata.yaml` and `releases/update.json` beneath the configured remote root, currently `/blux`. CI's package-upload endpoint is separate from this SFTP connection.
- Recheck the successful CI run for the exact tag and SHA, the frozen hashes, and the live metadata immediately before publishing. Stop if a newer beta has superseded this release. If unrelated remote fields or history changed, reconcile them and revalidate the snapshots before uploading.
- Upload only the two frozen files, using a temporary sibling and atomic rename where supported. Publish `downloaddata.yaml` first and `update.json` last so the download page is ready when the updater announces the beta. Read back each file and compare its bytes or hash with the snapshot. For transient errors, check remote state before retrying, with at most two retries. If one file is already verified, resume the other. Retain the checkpoint if credentials, CI, or publication block completion.

Report the version, tag and SHA, successful CI run URL, and which remote metadata files were verified. If any required step is pending, state exactly what remains.
